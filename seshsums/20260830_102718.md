2. **Ran a second experiment (`training-scan-5000`)** extending the same architecture's `:steps` scan to include 5000, to demonstrate cross-experiment model reuse. Confirmed empirically (not just by code-reading) that the four existing 1000/2000/3000/4000-step checkpoints' file mtimes were byte-for-byte unchanged after the run, and only one new `:trained` event (for 5000) appeared in `build.log` — only the missing value was trained, in one run, from scratch.

3. **User asked whether checkpoint-resume (loading an existing model's weights and training forward from them) was feasible**, to get real savings when extending an existing shorter run rather than just avoiding duplicate work within one scan call. Explained the mechanism and its real cost: the checkpoint format doesn't persist Adam's optimizer state, so a "resumed" run's momentum would restart from zero partway through — making its optimization trajectory genuinely different from a continuous run of the same nominal step count, not just a performance shortcut. Started drafting a design (automatic vs. opt-in trigger, `:resumed-from` provenance tracking) but the user shelved it outright once the comparability risk was clear: **not implemented, deliberately**.

4. **Ran a third experiment (`training-scan-confirm`)** re-scanning the exact same `1000 2000 3000 4000` range with nothing new to train. Confirmed: whole run (SBCL startup + ASDF load + 4 checkpoint loads + full test scoring) took 5.24 seconds wall time, zero step/milestone/training log lines, and the registry's entry count and `:trained` count were completely unchanged (only 4 new `:evaluated` audit lines were appended, as expected).
