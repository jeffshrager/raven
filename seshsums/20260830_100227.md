## What happened

1. **Set up `experiments/training-scan/manifest.lisp`.** Chose `corpus/poeall.txt` over `corpus/poeall-clean.txt` after diffing them — the "clean" corpus turns out to just delete rare characters outright (`x2+px` → `x2px`, `MAELSTRÖM` → `MAELSTRM`) rather than fix anything, so it's a regression, not a cleanup. Benchmarked the real architecture/corpus (~100ms/step) to give an honest ETA before handing it off.

2. **User spotted a real gap and asked for a fix**: if a training run crashes after a mid-run auto-checkpoint has already been written, the registry would show no trace at all — an orphaned `.ravn` file. Implemented a three-state lifecycle for `models/directory.lisp` entries: `:incomplete` (written before training starts) → `:completed` (final loss recorded) or `:failed` (error text recorded, error still re-signaled to the caller). `find-model-by-spec` only ever reuses `:completed` entries. Verified with a new `test-jig` failure-path check (bad corpus path → `:failed` entry + `:training-failed` build.log line).

3. **User then realized a genuine efficiency win** ("save all the checkpoints as real models rather than overwriting... run the LONGEST scan first and the rest will magically be there"): since a `:scan` over `:steps` with everything else fixed produces models that are literally prefixes of each other, one continuous run for the largest value can satisfy every smaller value along the way. Implemented this as a milestone mechanism:
   - `train-loop` gained a generic `:milestones`/`:on-milestone` hook (a callback fired at specific step counts, independent of the existing overwrite-in-place `:checkpoint-every` crash-safety mechanism).
   - New `train-with-milestones` uses it to register a full, independent `:completed` directory entry at every requested step count in one run (only training whichever counts aren't already `:completed`, up to the largest missing one) — reusing the same `:incomplete`/`:failed` crash-safety pattern from (2) for the run as a whole.
   - `resolve-experiment-models` now detects `:steps` among the scanned keys and routes through this path automatically (composed with cartesian expansion of any *other* scanned keys).
   - `test-jig` gained a dedicated check proving the mechanism fires exactly one `:training-started` / N `:trained` events (not N/N), plus a full-reuse re-run check. All 20 test-jig assertions pass.
   - A 4-value scan like `(:scan 1000 2000 3000 4000)` now costs 4000 total training steps instead of 10000.

4. **Actually ran `training-scan`.** Hit a self-inflicted snag: an earlier attempt to background the run via a bare shell `&` wasn't fully killed before relaunching properly through the harness's tracked background mechanism, leaving one stray orphaned `:incomplete` registry entry (no checkpoint file, since it died before its first milestone). Cleaned that one up; left the original pre-existing interrupted-run leftover in place per the user's explicit "don't worry about it" instruction. Final run reused the existing 1000-step model and produced 2000/3000/4000 in one continuous run, confirming the mechanism works on real (not just synthetic) data. Final loss: 2.45 → 2.39 → 2.32 → 2.28 across step counts; test-suite mean-NLL trends the same way with expected noise at this undertrained stage (7 challenges/model).

5. **Updated README** to match: `build.log` event list (now `:training-started`/`:trained`/`:training-failed`/`:evaluated`), and `test-jig`'s description (now covers the sweep/reuse/milestone/failure paths, not just the original two-value sweep).
